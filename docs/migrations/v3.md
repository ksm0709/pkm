# Migrating to PKM v3

PKM v3 removes the embedded answer-generation and scheduled-task runtime. The
upgrade keeps the vault, direct knowledge tools, and web editing surfaces while
moving cross-note synthesis to the agent host.

## What v3 removes

- **CLI:** the natural-language answer command and scheduled-task command group.
- **MCP:** the answer-generation proxy tool. FastMCP now exposes retained direct
  tools only.
- **HTTP:** the streamed answer endpoint and scheduled-task endpoints, including
  their query-token exception and stream keepalive behavior.
- **Frontend:** answer/session pages, scheduled-task pages, navigation entries,
  browser session state, and stream client code.
- **Runtime:** the isolated LLM worker, sandbox, model/provider adapter,
  credential manager, task queue, scheduled-task scheduler/history runtime, and
  answer-session orchestration.
- **Dependencies:** the embedded agent and LLM-provider packages. The optional
  `sentence-transformers` and `numpy` search dependencies remain available.

## Replacement: direct tools and host-side synthesis

The agent host owns synthesis in v3. Use this sequence:

1. Call `search` to find relevant starting points.
2. Call `get_note_neighbors` on promising results. Follow at most two graph
   depths in total.
3. Call `read_note` for every source selected as evidence.
4. Synthesize the answer in the agent host, citing or linking the notes used.

Do not synthesize from snippets alone. Search and graph output identify sources;
`read_note` supplies the evidence.

## What remains

- Daily notes, daily subnotes, atomic notes, tags, backlinks, typed relations,
  consolidation markers, and partial note edits.
- PDF/data-file viewing and upload, note/data/PDF annotations, and safe previews.
- Semantic search, index rebuilds, graph neighbors, clusters, hubs, and graph
  health tools.
- Vault discovery and management, editor/graph/web configuration, and the local
  web app.
- MCP over stdio with FastMCP direct-tool discovery.

## Legacy data handling

The v3 activation keeps durable v2 state in place but does not read it. This
makes a supported rollback reversible without importing obsolete formats:

- `~/.config/pkm/workflow.json`
- vault-level `.pkm/workflow.json`
- vault-level `.pkm/workflow-history.jsonl`
- old model/provider/reasoning keys in `~/.config/pkm/config`
- saved model-provider credentials in the system keyring service `pkm` or the
  fallback file `~/.config/pkm/secrets.env`
- browser keys matching `pkm.askSession.*`

These artifacts are inert under v3. Do not delete them if rollback is a
possibility. Browser storage and credentials remain on the machine until the
user clears them; v3 neither displays nor consumes them.

The exception is the ephemeral queue:

- `~/.config/pkm/task_queue.json` is deleted during v3 activation.
- It is intentionally **not archived** because queued payloads may contain
  secrets or other sensitive request content.
- Deleted queue entries cannot be restored by rollback.

## Activation checklist

1. Install the hardened bridge **v2.96.6** before v3. Earlier bridge releases
   added service quiescing, one-line installer cleanup, and fail-closed restart
   behavior in stages. v2.96.6 is the first bridge that also normalizes download
   failures, prints complete systemd recovery commands, and reloads the
   synchronized unit before a successful restart. It leaves the service stopped
   until reinstall, fresh post-update synchronization, and version verification
   all succeed.

   For a persistent Git checkout:

   ```bash
   pkm update v2.96.6
   pkm --version
   ```

   For the default one-line/non-Git installation, whose v2.96.1 updater cannot
   select a tag, use the tagged installer:

   ```bash
   curl -fsSL https://raw.githubusercontent.com/ksm0709/pkm/v2.96.6/cli/install.sh \
     | PKM_INSTALL_REF=v2.96.6 bash
   pkm --version
   ```

   Do not continue unless the version is `2.96.6`.
2. Stop any manually launched `pkm daemon run` process. The v2.96.6 updater
   automatically stops an active `pkm-web.service`, verifies it is inactive
   before mutating source or packages, runs the v3 post-update scrub, and starts
   the service again only after activation and version verification succeed. On
   failure it leaves the service stopped and prints an explicit recovery command.
3. Install v3 through the hardened bridge:

   ```bash
   pkm update v3.0.0
   pkm --version
   ```

   If service recovery is ever required, use the exact command below and inspect
   its status rather than starting a second daemon:

   ```bash
   systemctl --user daemon-reload
   systemctl --user restart pkm-web.service
   systemctl --user is-active pkm-web.service
   ```
4. Verify `~/.config/pkm/task_queue.json` is absent. Do not reconstruct it from
   backups: queue payloads may contain secrets and retired tasks must not replay.
5. Reconnect MCP clients so they perform fresh `tools/list` discovery.
6. Verify retained note, search, index, graph, PDF/data, annotation, and web
   operations.
7. Update agent prompts to use `search` → `get_note_neighbors` → `read_note` →
   host synthesis.

For a temporary return to v2, use the
[v2.96.1 rollback procedure](../rollback-v2.96.1.md).
